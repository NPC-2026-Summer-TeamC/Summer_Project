# 606호에 어서오세요

## 1. 프로젝트 버전

> Unity 6000.3.11f1

## 2. Git LFS 사용법

이미지, 오디오, 폰트, 3D 모델 등 대용량 바이너리 파일 관리를 위해 Git LFS를 사용합니다.

1. https://git-lfs.com/ 에서 다운로드 후 설치
2. 프로젝트 폴더에서 터미널을 열고 `git lfs install` 입력 (최초 1회만)
3. `.gitattributes`에 대상 확장자가 이미 등록되어 있으므로 추가 설정은 필요 없습니다.
4. 이후에는 평소처럼 `git add`, `git commit`, `git push`를 하면 대상 파일은 자동으로 LFS가 처리합니다.

## 4. 주석 컨벤션

스크립트 작성 시 의미 있는 주석을 남겨주세요. 함수/로직의 "왜"와 "어떻게"를 설명하는 주석은 좋지만, 코드만 봐도 알 수 있는 내용까지 전부 주석 달 필요는 없습니다.

✅ 좋은 예 (함수 목적과 사용법 설명)
```cs
// 플레이어가 타일을 드래그할 때 호출됨. 이동 가능 여부는 RuleValidator에서 별도 검증
public void OnTileDrag(Vector2 pos) { ... }
```

❌ 지양할 예 (단순 변수에 불필요한 주석)
```cs
int count = 0; // count 변수
```

## 5. 중괄호 컨벤션

함수는 여는 중괄호(`{`)를 다음 줄로 내리고, `if`/`while` 등 제어문은 같은 줄에 붙여서 작성합니다.

✅ 함수 - 줄바꿈 후 `{`
```cs
public void OnTileDrag(Vector2 pos)
{
    ...
}
```

✅ `if`/`while` 등 제어문 - 같은 줄에 `{`
```cs
if (isValid) {
    ...
}

while (hasNext) {
    ...
}
```

## 6. 폴더/에셋 구조 컨벤션

`Assets` 폴더 하위 구조는 다음 기준을 따릅니다. 새 폴더를 만들기 전에 기존 폴더 중 적합한 위치가 있는지 먼저 확인하고, 애매하면 팀원과 상의합니다.

| 폴더 | 용도 | 규칙 |
|---|---|---|
| `Assets/Scripts` | C# 스크립트 | 역할별 하위 폴더로 분류 (`Data`, `Managers` 등). 특정 기능 전용 스크립트가 늘어나면 기능명 폴더를 새로 만들어 정리 |
| `Assets/Prefabs` | 프리팹 | 기능/카테고리가 늘어나면 하위 폴더로 분류. 파일명은 네이밍 컨벤션의 `기능명_PF` 규칙을 따름 |
| `Assets/Scenes` | 씬 파일 | 정식 씬은 최상위에 두고, 테스트용 씬은 `Scenes/Tests`에 위치 |
| `Assets/Sprites` | 이미지/스프라이트 | 용도별 하위 폴더로 분류 (예: `UI`, `Tile`, `NPC`, `Item`) |
| `Assets/Audio` | 사운드 | `BGM`, `SFX` 등 용도별 하위 폴더로 분류 |
| `Assets/Settings` | URP 등 프로젝트 설정 에셋 | Unity가 자동 생성하는 폴더 - 임의로 구조를 변경하지 않음 |
| `Assets/TextMesh Pro` | TMP 리소스 | Unity가 자동 생성하는 폴더 - 임의로 구조를 변경하지 않음 |

## 7. 작업 시 주의사항⚠️

- **같은 씬 파일을 여러 명이 동시에 수정하지 마세요.** 씬/프리팹 단위로 작업자를 나눠서 진행합니다.
- 작업 **시작 전**: GitHub Desktop에서 **Fetch → Pull**을 먼저 진행하고 시작합니다.
- 작업 **완료 후**: 반드시 **Push**까지 완료합니다. 로컬 커밋만 하고 올리지 않으면 다른 팀원이 받을 수 없습니다.
- 본인 담당 구역 외의 씬/프리팹은 임의로 수정하지 않습니다. 수정이 필요한 경우 담당자와 먼저 협의합니다.

## 8. 이슈 관리

- 버그 발견 또는 할 일이 생기면 GitHub **Issues**에 등록합니다.
- 제목 + 간단한 설명 정도로 작성합니다.
- 라벨(`버그` / `기능`) 중 하나를 선택하고, 담당자를 Assignee로 지정합니다.

## 9. GitHub Project (칸반보드)

- 저장소 상단 **Projects** 탭에서 확인합니다.
- 작업 시작 시 본인이 `Status`를 `In Progress`로 변경합니다.
- PR에 이슈를 연결(`Close #번호` 또는 `Related to #번호`)하면 작업 진행 상태를 효율적으로 관리할 수 있습니다.

## 10. 브랜치 전략

```
main                  → 항상 실행 가능한 안정 버전
develop               → 기본 통합 개발 브랜치
feature/이름-기능명   → 기능 개발용 브랜치
fix/이름-내용         → 버그 수정용 브랜치
docs/이름-내용        → 문서 작업용 브랜치
```

- `main`, `develop`에는 직접 push가 불가능하며 **PR을 통해서만 병합**됩니다.
- 새 작업 시작 시:
  1. Develop에서 새 브랜치 생성 (예: `feature/jimin-tile-drag`)
    - 브랜치를 생성하기 전에 반드시 **Fetch → Pull**
  2. 작업하기
  3. 로컬 커밋 후 **Push**
    - 첫 브랜치 생성 시 Push 대신 **Publish**가 뜹니다.
  4. PR 생성 후 Merge (팀장이 수행)

## 11. 커밋 컨벤션

아래 이모지를 커밋 메시지 앞에 붙여서 작성하며, 메시지 끝에는 해당 작업과 관련된 **(#이슈번호)** 를 반드시 포함합니다. 누가 작업했는지는 따로 명시하지 않습니다.
커밋은 최대한 작은 단위로 하는게 좋습니다.
> <이모지><태그>: <설명> (#이슈번호)

| 이모지 | 태그 | 설명 | 커밋 메시지 형식 예시 |
|---|---|---|---|
| ✨ | `FEAT` | 새로운 기능 추가 | `✨FEAT: 타일 드래그 기능 구현 (#12)` |
| 🎨 | `STYLE` | UI/비주얼 조정 (기능 변화 없음) | `🎨STYLE: 메인 메뉴 버튼 색상 변경 (#15)` |
| 🛠 | `FIX` | 코드 오류 수정, 오타 정정, 로직 버그 해결 | `🛠FIX: 타일 드래그 시 씬 이탈 버그 수정 (#18)` |
| 🔧 | `REFACTOR` | 기능 변화 없는 코드 구조 개선 | `🔧REFACTOR: 데이터 검증 로직 모듈화 (#22)` |
| 📂 | `DOCS` | README.md 작성, 문서 작업 | `📂DOCS: 커밋 컨벤션 안내 가이드 수정 (#5)` |
| 📦 | `CHORE` | 파일 이동, 폴더 구조 변경 등 단순 관리 작업 | `📦CHORE: 사운드 리소스 폴더 위치 이동 (#30)` |

> 💡 **주의 사항**
> - 이슈 번호 앞에는 반드시 샵(`#`) 기호를 붙여야 GitHub에서 해당 이슈와 커밋이 자동으로 링크됩니다.
> - 관련된 이슈가 없는 단순 작업일 경우 `(#이슈번호)` 부분을 생략할 수 있습니다.

## 12. Pull Request (PR) 규칙

- `develop`으로 병합할 때는 반드시 PR을 생성합니다.
  - 이번 PR로 이슈가 완전히 완료된다면 `Close #이슈번호`를 작성합니다. (머지 시 자동 종료)
  - 이슈 작업이 진행 중이거나 연관 표시만 필요하다면 `Related to #이슈번호`를 작성합니다. (자동 종료되지 않음)
  - `추가 사항`은 필요할 때만 작성하고, 없으면 섹션을 삭제합니다.
- **최소 1인의 리뷰 승인이 있어야 머지 가능**합니다.
- 본인이 작성한 PR은 직접 머지하지 않고, 리뷰를 먼저 요청합니다.
